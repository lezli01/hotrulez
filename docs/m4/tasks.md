## Implementation Decisions (grilled 2026-07-03 — please confirm)

These resolve the open *implementation* branches surfaced by a `/grill-me` pass over
this task list while you were away from the keyboard. Each was decided with a
recommended default, is cheaply reversible, and is grounded in a verified codebase or
SDK fact (in *italics*). They sit below the eight higher-level decisions in
`docs/spec.md`; nothing here reopens those.

### Shared doc-prose table (`FirebaseRulesDocs`)

1. **Flat prose map, dialect-gated through `RulesService`.** `FirebaseRulesDocs` is a
   flat `Map<fullPath, Entry(title, summaryHtml, docUrl)>` keyed by the same
   whitespace-stripped member paths `RulesService` uses (`request.auth`,
   `resource.size`, …). The documentation provider validates a member against
   `RulesService.membersFor(forElement)` **before** fetching prose, so a Storage-only
   member (`resource.size`) never shows prose inside a Firestore file. `RulesService`
   stays the single vocabulary/validity source; the table is pure prose. *(Rejected: a
   per-dialect nested map — it would duplicate the split `RulesService` already owns and
   risk drift.)*
2. **Divergent globals get one shared phrasing.** The only full-path keys whose
   *meaning* differs by dialect are the umbrella globals `resource` and
   `request.resource` (existing document vs stored object; document-being-written vs
   object-being-uploaded). These get a single summary naming both services rather than a
   dialect override; a `(dialect, path)` override map is deferred until a real
   divergence needs it. *(Every leaf member below them is dialect-exclusive — verified
   against `RulesService.FIRESTORE.members` / `.STORAGE.members` — so no other key
   collides.)*
3. **Entries store CONTENT-ready HTML fragments; the provider owns section structure.**
   `title` becomes the `DocumentationMarkup` DEFINITION line, `summaryHtml` the CONTENT
   body; fragments use only Swing-safe inline markup (`<code>`, `<b>`).
4. **Namespace *members* stay deferred/`UNCONFIRMED`.** The table documents the
   namespace itself (`math` → "math functions"), not `math.abs`/`timestamp.date`; the
   integrity test carries an explicit deferred list so the gap is visible.
5. **`docUrl` is the per-category Firebase page** (the pages in spec "Documentation
   Sources"), not a per-member anchor (anchors are brittle/undocumented). `getUrlFor`
   returns it.
6. **Helper entries carry the `path` signature string**, reused verbatim by parameter
   info's one-line note — single source.

### Feature 1 — Structure view

7. **Root children = top-level `service`/`match`/`function`** via
   `PsiTreeUtil.getChildrenOfType(file, …)`; `rules_version` is not surfaced. *(Grammar:
   `top_level_decl` cannot produce a top-level `allow`; the file is a plain
   `PsiFileBase` with no typed top-level accessor, mirroring
   `FirebaseRulesScopes.functionsDeclaredIn`.)*
8. **`allow` label is rebuilt from the method list's `IDENTIFIER` leaves**, joined
   `", "`, prefixed `allow ` → `allow read, write`. *(`FirebaseRulesMethodList` is an
   empty PSI interface and `.text` can carry interleaved comments/whitespace — the same
   reason `receiverKey` walks tokens.)*
9. **Icons (platform `AllIcons.Nodes.*`, no new assets):** service → `Package`,
   match → `Folder` (path-scope), function → `Method`, allow → `Property`.
10. **`getSuitableClasses` = the four surfaced PSI classes** (service / match /
    function / allow declarations) so the nav bar + "select in" track the caret.
11. **Null label sources fall back to a stable placeholder** (`service`/`match`/
    `function`/`allow`) rather than dropping the node — partial tree, never an
    exception, during editing.

### Feature 2 — Code folding

12. **Fold ranges are the `FirebaseRulesBlock` / `FirebaseRulesFunctionBody` nodes
    directly** (service, match, function) — *grammar: both nodes span `{ … }` inclusive*,
    so the head stays visible with no manual range math. Block comments: a descriptor
    per `BLOCK_COMMENT` leaf.
13. **Emit only with both braces present and a non-empty interior** (a block/body with
    ≥1 child; a block comment spanning more than one line). *(Grammar: `block` and
    `function_body` are `pin=1` on `{`, so an in-progress unclosed block has a null
    `RBRACE` child — the guard suppresses the bogus fold; single-line block comments gain
    nothing from folding.)*
14. Placeholders `{…}` / `/*…*/`; `isCollapsedByDefault` false everywhere (per spec).

### Feature 3 — Quick documentation

15. **Built-in targets are represented by the PSI element under the caret itself.**
    `getCustomDocumentationElement` returns the `reference_expression` /
    `member_expression` / method-list identifier / call callee as-is; `generateDoc`
    branches on element type + dialect. No synthetic PSI. *(Confirmed against the SDK
    `AbstractDocumentationProvider` tutorial — the same context-leaf → target pattern.)*
16. **User symbols:** function → `function name(params)` + the contiguous run of
    immediately-preceding `LINE_COMMENT`s (or a single preceding `BLOCK_COMMENT`),
    markers stripped; parameter → `parameter 'x' of function f`; `let` → `let x = <expr>`
    (expression text, truncated ~100 chars); path/recursive wildcard → `path variable
    'x' captured by match /…` ("recursive path variable" for `{x=**}`).
17. **Ctrl-Q works on the declaration too**, not only uses (map a name identifier whose
    parent is a `FirebaseRulesNamedElement` to that element).
18. **Dispatch is purely structural:** members only ever appear as
    `member_expression.identifier`, globals only as `reference_expression` — no
    ambiguity, no type inference. Unknown member / unresolved name → `null`.
19. **`getUrlFor` returns a URL only for tabled built-ins**; user symbols → `null`.

### Feature 4 — Parameter info

20. **Presentation model** `data class SignaturePresentation(params: List<String>,
    note: String?)` as the handler's `P`; `updateUI` joins `params` with `", "`, bolds
    the current index, appends `note`.
21. **Callee dispatch:** `reference_expression` → `FirebaseRulesScopes` resolve to user
    `FirebaseRulesFunctionDeclaration`(s), params from `parameterList` (poly-variant →
    one item per declaration); else if the name ∈ `bareHelpersFor(service)` → single
    `path` param + note; `member_expression` `firestore.<get|exists>`
    (`CROSS_SERVICE_HELPERS`) → single `path` param + note; any other `member_expression`
    (e.g. `math.abs`) → no items (deferred).
22. **User function shadows a same-named helper** (resolver first; helper only when
    resolve is empty) — matches language scoping.
23. **Current parameter = count of top-level `COMMA` children of the `argument_list`
    before the caret**; nested commas (map/list/ternary args) ignored; trailing comma
    tolerated; over-count clamped (no arity validation). *(Grammar: `argument_list`
    allows a trailing comma.)*

### Shared / refactor, tests, registration

24. **`receiverKey` is extracted to `references` (beside `RulesService`)** — e.g.
    `FirebaseRulesMemberPath.receiverKey(...)` — and called by both the completion
    contributor and the documentation provider (no duplication). *(completion already
    imports `references`; no cycle.)*
25. **Neutral files use the union** (`membersFor(null)` / `bareHelpersFor(null) →
    Firestore`) for docs + parameter info, exactly as completion does today.
26. **Context7 EP re-check is the first coding step** for all four EPs (ground rule);
    the two riskiest APIs — `AbstractDocumentationProvider`
    (`generateDoc`/`getCustomDocumentationElement`/`getUrlFor`) and
    `codeInsight.parameterInfo` / `ParameterInfoHandler` — were already confirmed current
    for 2025.2 during this pass.
